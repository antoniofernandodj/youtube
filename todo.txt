BUG 1 — Thumbnails/avatares aparecem PRETOS (ou em branco) na grade
===========================================================================

STATUS: RESOLVIDO. Causa raiz encontrada lendo o código-fonte do motor
(não era GPU/Vulkan — aquilo era uma pista falsa, ver histórico abaixo).

CAUSA RAIZ CONFIRMADA (lida direto no código, não é suposição):
`if="{chave}"` sozinho (sem equals/not_equals/one_of/contains/empty/
not_empty) NÃO significa "essa chave tem valor" — significa "essa chave é
um FLAG booleano marcado". A implementação (duas cópias idênticas em
espírito, uma em cada arquivo):

  glacier-ui/src/eval.rs:930 (usada pela avaliação de if=/else-if= genérica)
    fn is_truthy(s: &str) -> bool {
        matches!(s.trim().to_ascii_lowercase().as_str(),
            "true" | "1" | "yes" | "on" | "sim")
    }

  glacier-ui/src/widget.rs:447 (usada por widgets tipo checkbox/toggle)
    pub(crate) fn is_truthy(s: &str) -> bool {
        let s = s.trim();
        igual_ci(s, "true") || igual_ci(s, "yes") || igual_ci(s, "on")
            || igual_ci(s, "sim") || s == "1"
    }

É uma ALLOWLIST, não um "vazio/false/0 = falso, resto = true". Uma URL ou
caminho de arquivo (ex.: "/home/.../l37veKnjePU.jpg") NUNCA bate com
nenhum desses cinco valores — logo `if="{thumb}"` é SEMPRE falso quando
`thumb` é uma miniatura de verdade, e o `<container else class=
"miniatura_vazia">` (placeholder escuro) é o que sempre aparece no lugar.
Isso é 100% determinístico, não depende de GPU, driver, for-each,
componente, scrollable ou nada disso — por isso nenhuma das teorias de
composição/GPU explicava o comportamento visto.

Por que a interpolação de texto `{thumb}` mostrava o valor certo ao lado
do placeholder preto: interpolação de texto não passa por is_truthy() —
ela só substitui a chave pelo valor cru. Só quem usa is_truthy() é o
avaliador de if=/else-if= (eval.rs) e os widgets de estado marcado tipo
checkbox (widget.rs) — dois caminhos de código totalmente diferentes do
de interpolação, o que é exatamente por que os dois pareciam
"discordar" sobre se {thumb} era truthy.

`not_empty`/`empty` TAMBÉM não servem pra isso — são especificamente para
listas JSON (`json_array_is_empty`, eval.rs:999 faz
`serde_json::from_str::<Value>(value)` e só considera "não vazio" um
Array JSON de fato; uma string simples tipo uma URL SEMPRE conta como
"vazio" ali, porque não faz parse como array).

CONCLUSÃO: não é bug do motor — é comportamento deliberado (documentado
no próprio comentário do código: "Whether a context string should count
as 'checked'/true", pensado pra checkbox/toggle, não pra "essa string
tem conteúdo?"). O idioma certo pra "renderiza se a chave tiver um
valor não-vazio" é comparação explícita contra string vazia:
`if="{chave}" not_equals=""` — isso usa o branch `not_equals` de
eval_condition (eval.rs:954), que faz comparação de string pura via
process_tpl, sem passar por is_truthy nem por parse de JSON.

FIX APLICADO em views/app.gv (dois lugares):
  - VideoCard: `<image if="{thumb}" not_equals="" source="{thumb}" .../>`
  - Tela de vídeo: `<image if="{video_thumb}" not_equals=""
    source="{video_thumb}" .../>`
O `<container else ...>` (placeholder) continua funcionando igual —
`else` ainda amarra no resultado do `if` anterior (`last_if`), só que
agora o `if` de fato reflete "tem thumbnail ou não".

NÃO precisou de mudança nenhuma no motor (glacier-ui) — é 100% fix de
uso no lado do app. Ficou pra nota, pro caso de valer documentar melhor
no AGENTS.md do glacier-ui que `if="{chave}"` sozinho é semântica de
FLAG booleano, não de "tem valor".

BUG 2 — "Em alta" (e potencialmente qualquer fetch) trava pra sempre
===========================================================================

STATUS: NÃO RESOLVIDO. Causa raiz aparenta estar fundo no motor
(glacier-ui/iced/tokio), não na rede, não no app.

CONTEXTO IMPORTANTE (usuário, 2026-09-13): o erro é ESPECÍFICO da tela

- Endpoint/parâmetros: `/videos?chart=mostPopular&...` vs `/search?q=...`
  — respostas de tamanho e formato diferentes (busca costuma paginar
  menos itens por padrão; populares pode vir com mais itens/campos).
- Timing de disparo: "Em alta" carrega no `init()` da tela (dispara
  fetch imediatamente ao entrar na home), enquanto busca só dispara
  depois de o usuário digitar e confirmar — ou seja, "Em alta" é a

  runtime/executor do iced ainda não está totalmente "pronto" pra

  um pequeno delay/segunda leva de update) e ver se sair do `init()`

- Cache: com o cache de 10min já implementado, popular fica cacheado
  também — reconfirmar se o hang acontece mesmo em cache HIT (não

PENDENTE — suporte a múltiplas abas, com baixo consumo de RAM
===========================================================================

STATUS: NÃO INICIADO. Requisito do usuário, anotado em 2026-09-13.

REQUISITO: o app precisa suportar várias abas abertas ao mesmo tempo
(ex.: um vídeo tocando numa aba, navegando/pesquisando em outra), com
estas prioridades explícitas do usuário, nesta ordem de importância:
1. Baixo consumo de RAM sempre — não é "aceitável gastar mais RAM por
   simplicidade", é um requisito duro.
2. NUNCA alocar memória desnecessariamente — cada aba não usada
   ativamente não deve segurar recursos (imagens decodificadas, buffers
   de webview, handles de vídeo, etc.) que uma aba inativa não precisa.
3. Escolher a MELHOR estratégia pra montar/desmontar a tela de cada aba
   — ou seja: decidir com cuidado QUANDO uma aba deveria estar totalmente
   viva (montada, consumindo RAM) vs. suspensa/descartada (desmontada,
   RAM liberada) vs. talvez um meio-termo (mantém só o estado/dados leves
   em Lua, descarta a árvore de widgets e os assets pesados tipo
   webview/imagens até o usuário voltar pra aba).

ANTES DE IMPLEMENTAR NO APP: fazer uma checagem no PRÓPRIO MOTOR
(glacier-ui) pra garantir que ele dá suporte de verdade ao melhor
resultado possível aqui — não adiantar montar a solução no app se o
motor não tiver a peça certa por baixo. Pontos a checar no glacier-ui:
- Existe hoje algum conceito de "aba"/múltiplas telas simultâneas dentro
  de UMA janela (não confundir com `open_window` multi-janela, que já
  existe) — ou isso precisaria ser construído inteiramente no app via
  `<template if=.../>` trocando qual conteúdo aparece? Nesse caso, cada
  "aba" escondida ainda ficaria com a árvore de widgets montada
  (só invisível), o que provavelmente NÃO bate com "baixo consumo de
  RAM" — precisa confirmar se árvores escondidas por `if=`/`else` são
  de fato DESALOCADAS (via eval_owned/expand_children reconstruindo do

   ANTES de escrever UI pra abas — a estratégia de retenção de estado é
   a decisão que mais importa aqui, a UI de abas em si é trivial depois.
3. Se o motor precisar de uma peça nova (ex.: um jeito explícito de
   "descartar e recriar" uma sub-árvore sob demanda, ou invalidação de
   cache de imagem por LRU/tamanho máximo), implementar isso no
   glacier-ui primeiro, do jeito de sempre (bump + commit + publish).
4. Só depois disso, implementar a UI de abas no app (views/app.gv +
   app.luau) usando a estratégia decidida.

PENDENTE — exibir imagens direto da RAM (não só as que estão em disco)
===========================================================================

STATUS: NÃO INICIADO. Requisito do usuário, anotado em 2026-09-14.

REQUISITO: os elementos de UI que hoje exibem imagem (`<image source=...>`,
usado em VideoCard/avatares/thumbnails etc.) só sabem exibir imagem a
partir de um caminho em disco (ex.: arquivo já baixado em
`~/.local/share/youtube/cache/`). Precisam também ser capazes de exibir
uma imagem que existe só em memória (bytes já em RAM, sem ter passado por
disco) — por exemplo bytes recém-baixados antes de serem gravados no
cache, ou gerados/decodificados em memória.

IDEIA LEVANTADA PELO USUÁRIO: usar codificação base64 (ex.:
`source="data:image/jpeg;base64,{dados_base64}"` ou equivalente) como
possível caminho pra passar bytes de imagem direto via string, sem
depender de um caminho de arquivo.

A CHECAR (antes de implementar no app):
- Se `<image source=...>` no glacier-ui hoje só aceita caminho de
  arquivo/URL, ou se já existe suporte a data URI (`data:`) —
  ler `cached_image_handle`/`assets` em glacier-ui/src/widget.rs pra
  confirmar o que `source` aceita hoje e onde seria o ponto de extensão.
- Custo de base64 em string Lua pra imagens grandes (overhead de ~33% de
  tamanho + tempo de encode/decode) — avaliar se vale a pena versus outro
  mecanismo (ex.: motor aceitar bytes crus/handle de memória diretamente,
  sem passar por string/base64).
- Ver se isso se conecta com o item de "múltiplas abas com baixo consumo
  de RAM" logo abaixo — cache de imagem decodificada em memória é um
  tema relacionado.

PRÓXIMOS PASSOS SUGERIDOS:
1. Ler glacier-ui/src/widget.rs (`cached_image_handle`/`assets`) pra
   entender exatamente como `source=` é resolvido hoje (arquivo vs URL vs
   outros esquemas) e se dá pra estender pra aceitar bytes em memória
   (via data URI base64 ou outro mecanismo nativo).
2. Decidir a abordagem (data URI base64 é o caminho mais simples de
   implementar no lado do app sem mudar o motor; um esquema de "handle de
   memória" seria mais eficiente mas provavelmente exige mudança no
   glacier-ui).
3. Implementar e testar com um caso real (ex.: exibir uma thumbnail antes
   dela ser persistida em disco, direto dos bytes baixados).
